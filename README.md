# JudgeBench for Inspect AI

[JudgeBench](https://arxiv.org/abs/2410.12784) implemented as an [Inspect AI](https://inspect.aisi.org.uk/) eval, with position-consistency measurement added.

Tan et al., *JudgeBench: A Benchmark for Evaluating LLM-based Judges*, arXiv:2410.12784.

## What it measures

Most judge benchmarks score a judge against human preference. JudgeBench scores it against **ground truth**. Each sample pairs a question with two candidate responses where exactly one is objectively correct, drawn from benchmarks that have verifiable answers. The judge picks a response and is scored on whether it picked the correct one.

That framing is the point. A judge that consistently rewards fluent, confident, well-formatted wrong answers can score well on preference benchmarks and badly here. If you are using an LLM as a grader in your own eval pipeline, this measures the failure mode that actually costs you: the grader agreeing with a plausible wrong answer.

## Results

2,480 judgments, four full runs, all under grading hash `a054759f0aa17eb6`. Receipts in [`out/results.json`](out/results.json).

| judge | $/1M in-out | split | pairs | accuracy | position consistency | first-position rate | verdict parse |
|---|---|---|---|---|---|---|---|
| `gpt-5.6-luna` | 0.20 / 1.20 | gpt | 350 | **0.907** ±0.011 | 0.940 | 0.490 | 1.000 |
| `gpt-5.6-luna` | 0.20 / 1.20 | claude | 270 | **0.887** ±0.014 | 0.915 | 0.498 | 1.000 |
| `claude-haiku-4-5` | 1.00 / 5.00 | gpt | 350 | 0.829 ±0.014 | 0.834 | 0.480 | 1.000 |
| `claude-haiku-4-5` | 1.00 / 5.00 | claude | 270 | 0.739 ±0.019 | 0.811 | 0.472 | 1.000 |

**This is not a leaderboard.** Two models is not a ranking, and the interesting content is below, in which differences survive scrutiny and which do not.

### The cheaper judge wins, and the gap is real

Luna costs a fifth of Haiku 4.5 and beats it on both splits: **+0.079 (z = 4.4)** on gpt and **+0.148 (z = 6.4)** on claude. Both gaps are large relative to their uncertainty. Price is not a proxy for judge quality here, and the direction is the opposite of the usual assumption.

### No self-preference

The two splits are named for the model that *generated* the responses being judged, which sets up a self-preference test: does an OpenAI judge favor OpenAI-written responses?

It does not, and neither does the Claude judge favor Claude-written ones.

| judge | gpt split minus claude split | z | reading |
|---|---|---|---|
| `gpt-5.6-luna` | +0.020 | 1.1 | no detectable difference |
| `claude-haiku-4-5` | +0.090 | 3.8 | significantly **worse** on Claude-written responses |

If self-preference were present, each judge would do relatively better on its own family's split. Luna shows no split difference at all, and Haiku moves significantly in the **opposite** direction. The claude split is simply harder, and it is disproportionately harder for the weaker judge.

That conclusion needs both vendors. With only the OpenAI judge, luna's +0.020 is unfalsifiable: it could be mild self-preference or it could be split difficulty, and there is no way to tell from one vendor. The second judge is what turns a caveat into a result.

### Neither model is position-biased

All four runs land between 0.472 and 0.498 against an unbiased 0.500, every one within 1.3 standard errors. Whatever separates these judges, it is not a preference for whichever response appears first. That is exactly what accuracy alone cannot tell you, and it is why the positional tasks exist.

## Read accuracy against the baseline, not against zero

Labels are not evenly split. A judge that ignores both responses and always answers A scores:

| split | always-A accuracy |
|---|---|
| `gpt` | **55.1%** (193/350) |
| `claude` | **53.0%** (143/270) |

Any headline accuracy below roughly 55% is indistinguishable from not reading the responses.

## Tasks

| task | judgments | pairs | responses generated by |
|---|---|---|---|
| `judgebench_gpt` | 350 | 350 | `gpt-4o-2024-05-13` |
| `judgebench_claude` | 270 | 270 | Claude |
| `judgebench_gpt_positional` | 700 | 350 | `gpt-4o-2024-05-13` |
| `judgebench_claude_positional` | 540 | 270 | Claude |

Items come from four upstream benchmarks, all of which have verifiable answers: **LiveBench reasoning** (98 gpt / 51 claude pairs), **LiveBench math** (56 / 34), **LiveCodeBench** (42 / 31), and **MMLU-Pro** across 14 subjects (11 pairs each, 154 / 154). MMLU-Pro is therefore 44% of the gpt split and 57% of the claude split, not the whole of either.

The positional tasks present every pair twice, once as shipped and once with the two responses swapped. Swapping moves the correct content into the other slot, so the correct letter flips. Three metrics come out:

- **`position_consistency`**: fraction of pairs where the judge named the same response both times. A content-driven judge scores 1.0.
- **`first_position_rate`**: fraction of all verdicts naming A. Since every pair runs in both orders, a content-driven judge scores exactly 0.5. Distance from 0.5 is the pull toward a slot.
- **`verdict_parse_rate`**: fraction of replies containing a usable verdict, reported so a judge ignoring the output format is never mistaken for a judge getting answers wrong.

`accuracy` and `stderr` are Inspect's built-ins and run over judgments. **`stderr` treats the two orientations of a pair as independent samples, and they are not**: the same question and the same two responses are judged twice, once per order. The reported ± is therefore optimistic, and the effective sample size is the pair count (350 or 270), not the judgment count (700 or 540). The metric is left as shipped so the table stays comparable with the register listing and with 0.1.0. Read the intervals as a floor on the uncertainty; the gaps called significant above clear the bar by wide margins under either count.

The plain tasks are contained in the positional ones: the `original` orientation is exactly the plain run, so there is no need to pay for both.

## Usage

```bash
uv sync --extra providers
uv run inspect eval judgebench_inspect/judgebench_gpt_positional --model openai/gpt-5.6-luna
uv run inspect eval judgebench_inspect/judgebench_claude_positional --model anthropic/claude-haiku-4-5 --batch
```

The package registers an `inspect_ai` entry point, so tasks resolve by package name once installed. The file-path form, `src/judgebench_inspect/task.py@judgebench_gpt_positional`, still works from a checkout.

Scoring is deterministic. The model under test *is* the judge, so there is no grader model in the loop and no grader to validate.

All four runs above cost **under $5 in total**, including every smoke test.

## Design notes

**The two responses are delimited blocks, not lettered choices.** This looks like a formatting detail and is not. Roughly half the items come from MMLU-Pro, so candidate responses routinely contain their own `(A) ... (B) ... (C)` option lists while reasoning about the original question. Rendering the two responses as choices `A)` and `B)` puts two competing letter schemes in one prompt, and models answer the embedded question instead of judging. An early version of this harness did exactly that and scored 0.000, with the model confidently answering `(C)` on a two-option task. The verdict token is named `VERDICT` so it cannot collide with the dataset's own lettering.

**The last `VERDICT:` line is the verdict.** The prompt asks for reasoning followed by a closing verdict, so a judge that names one letter, reconsiders, and ends on the other has decided on the second. Inspect's built-in `pattern()` scorer takes the first match; 0.1.0 used it, and the register's review caught it. Task version 1 scores the last line, and the [CHANGELOG](CHANGELOG.md) names the one published judgment that changed.

**A reply with no verdict scores incorrect** rather than being coerced into a guess, and the parse rate is reported alongside so the two failure modes stay separable.

**Choice order is left as the dataset ships it** in the plain tasks, so results stay comparable with the paper. Position sensitivity is measured rather than shuffled away.

**The dataset is pinned** to revision `57dd5e0b9817d07f05ec8f45a91b2ce1e310e308`, so a rerun a year from now grades against the same items.

**A grading hash guards every receipt.** `src/judgebench_inspect/grading.py` digests the judge prompt, verdict pattern, dataset path, pinned revision, and the logic of `record_to_sample` with comments and docstrings stripped. It is stamped into every eval log and pinned by a test. Two runs are comparable only when their hashes match, so a change to grading fails a test instead of silently invalidating published numbers.

## Limitations

**The prompt is one reasonable phrasing**, not the paper's exact wording, so absolute numbers are not directly comparable to the published table. Relative comparisons between models run through this harness are.

**Standard errors are computed over judgments, not pairs.** The two orientations of a pair are not independent, so the intervals above are somewhat optimistic. The effective sample sizes are 350 and 270 pairs, not 700 and 540 judgments. This affects the size of the intervals, not the direction of the gaps, and the significant results here clear the bar by wide margins.

**Two judges is a small panel.** The self-preference conclusion rests on one model from each of two vendors. It rules out the effect for these two, not in general.

## Notes for anyone running this

**OpenAI batch enqueue limits count reserved output tokens, not actual.** `gpt-5.6-terra` rejected 700-, 250-, and 100-request batches with `token_limit_exceeded` against a 900,000 enqueued-token cap, while a 5-request batch went through. A reasoning model reserves a large fixed output budget per request, so batch sizing has to be derived from the reservation rather than from observed usage. Rejected batches are not charged.

Anthropic batches on this workload completed in roughly four minutes for 700 requests, at half the standard rate.

## Development

```bash
uv run pytest tests/ -q
uv run ruff check . && uv run ruff format --check .
uv run python scripts/extract_results.py   # regenerate out/results.json from logs-full/
uv run python scripts/scrub_logs.py        # sanitize logs for publication
uv run python scripts/scrub_logs.py --check
```

`scripts/scrub_logs.py` exists because unbatched runs capture Python tracebacks on retries, and those tracebacks embed absolute paths containing the operating user's home directory. The two unbatched runs behind the numbers above carried roughly 4,400 such paths each. `--check` re-scans the sanitized copies and exits non-zero if anything identifying survives, and the sanitized logs were verified to reproduce every published metric exactly.

`tests/test_readme_claims.py` parses this file and asserts every number in it against `out/results.json`, so the README cannot drift from the receipts.
